# Spike S2 — threads and memory of the tray

**Question:** with `ksni` 0.3.7 (`async-io`) and one `zbus` 5.19.0 connection whose executor is ticked
on the main thread (`internal_executor(false)`), which threads exist, and what does each tray item cost?

Run on 2026-11-18 in the GNOME session. Each release process was measured after 15 ticks (30 s)
using `spikes/tray/measure.sh`. Memory values use the units reported by Linux.

| Items | Threads (count and names) | Rss | Pss | D-Bus calls answered / ticks |
|---|---|---|---|---|
| 1 | 4 (`threads` ×2, `async-io`, `blocking-1`) | 3884 kB | 1937 kB | 15/15 |
| 3 | 4 (`threads` ×2, `async-io`, `blocking-1`) | 4016 kB | 2069 kB | 15/15 |
| 6 | 4 (`threads` ×2, `async-io`, `blocking-1`) | 4220 kB | 2277 kB | 15/15 |

**Per item:** (2277 − 1937) ÷ 5 = 68 kB Pss per additional item over this range. Each `ksni` item
opens its own session-bus connection. No `GetId` failures or timeouts appeared in the three logs. A
tray `update` that timed out would have ended the run instead of being logged like `GetId`; none
did, since all three runs reached 15 ticks.

**Threads:** the samples show the predicted main thread and shared `ksni` driver (both named
`threads`), the `async-io` reactor, and one `blocking-1` pool thread. `blocking-1` was still present
at 30 s in all three runs. Its eventual retirement was not measured.

**Finding for the invariant:** the main loop can drive the dedicated `zbus` connection, and increasing
the tray count from one to six did not add threads in these samples. Account for the shared tray
driver, the reactor and the observed pool thread alongside the daemon's own worker. This spike
measured one 30 s window per item count. Plan 11 measures the daemon's longer-running footprint.
The user deferred the roadmap invariant revision.
