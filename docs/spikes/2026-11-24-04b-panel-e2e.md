# Plan 04b — panel end-to-end run

Run on 2026-11-25 on Ubuntu 26.04.1 LTS, kernel 7.0.0-44, GNOME Shell 50.1, Wayland, on a laptop
with 4 cores and 8 logical CPUs, with `coretemp`. The run used the release build of `statsbard`
and `statsbar-panel` from `feature/panel-skeleton` (Tasks 1–6 staged on 4c96984), built with
rustc 1.100.0 by `cargo build --workspace --release --locked`, from
[the Plan 04b plan](../plans/2026-11-24-rust-statsbar-04b-panel.md).

No `statsbard` was running before the run. The daemon ran with the user's config; the one switch
the run changed (*Show CPU*) was set back, and the file compared equal to a copy taken before.
Tray clicks were dbusmenu `Event` calls over the session bus; the panel's buttons and labels were
pressed and read over AT-SPI (`Atspi` 2.0 from Python). The helper scripts are kept outside Git.
The power profile was `performance` throughout. Other builds ran on the machine during the run, so
CPU load swung by tens of points from one second to the next.

## Renderer

The panel was started by hand on the CPU page and left idle; after 10 s to settle, Pss was read from
`smaps_rollup` and CPU time from `stat` (utime + stime, 100 ticks a second) over 60 s.

| Run | Renderer | Pss start → end | Rss end | CPU over 60 s | Threads |
|---|---|---|---|---|---|
| 1 | `cairo` | 23637 → 24092 kB | 62300 kB | 36 ticks, 0.60 % | 13 |
| 2 | `ngl` | 127246 → 127183 kB | 210460 kB | 37 ticks, 0.62 % | 13 |
| 3 | `cairo` | 22848 → 23186 kB | 61500 kB | 41 ticks, 0.68 % | 13 |
| 4 | `ngl` | 50208 → 50149 kB | 132260 kB | 50 ticks, 0.83 % | 13 |

`cairo` has the lower Pss by 27–104 MB, with CPU time within the run-to-run spread, so
`launch::RENDERER` stays `cairo`. The two `ngl` runs differ by 77 MB; why was not measured.

## Commands

```bash
cargo build --workspace --release --locked
cargo tree -p statsbard -e normal | grep -c gtk
setsid target/release/statsbard &
GSK_RENDERER=cairo target/release/statsbar-panel --page cpu   # and ngl
grep Pss /proc/$PANEL/smaps_rollup; awk '{print $14+$15}' /proc/$PANEL/stat
# tray menus: com.canonical.dbusmenu GetLayout, and Event <id> "clicked", from Python Gio
# panel: Atspi do_action(0) on its buttons; names of its labels
free -b; top -b -n 4 -d 1; cat /sys/class/hwmon/hwmon*/temp1_input; cat /proc/uptime
grep syscr /proc/$DAEMON/io                    # every 20 ms around Refresh, each second at close
python3 -c 'import time; b=bytearray(800<<20); time.sleep(900)'   # stand-in
yes >/dev/null                                  # CPU stand-in
grep -E '^(Rss|Pss):' /proc/$DAEMON/smaps_rollup; ls /proc/$DAEMON/task | wc -l
```

The stand-ins were the only processes signalled, besides the panels and the daemon this run started.
‹stand-in› stands for the stand-in's process name, as the dialog and toasts showed it.

## Not seen

1. **The Uptime row changing on Refresh.** The row shows whole minutes, so a page sooner by under a
   second does not change it. The page Refresh asks for was read off the daemon's `syscr` instead.
2. **Clicks were not made in the GNOME UI.** Tray clicks were dbusmenu `Event` calls and the
   panel's were AT-SPI actions, which run the same handlers as a click.
3. **CPU figures under a steady load.** Builds ran beside the run, so usage moved by up to 35 points
   a second; the panel's figures fell within the swing of the `top` frames around them.
4. **The panel's own CPU in `top` (35 %)** was the AT-SPI tree walk of the helper; idle, the panel
   used 0.6–0.8 %, as in the renderer table.
5. **The daemon's Pss gap.** On a fresh start it is 2919 kB, 130 kB above Plan 03b's 2789 kB. Plan
   04a's 3285 kB was taken after page clients, like this run's 3174 kB. Where the 130 kB goes was
   not measured.
